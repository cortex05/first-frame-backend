# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Express 5 + Mongoose REST API (ES modules, plain JavaScript) backing the separate `first-frame` frontend repo. An **account** is the top-level tenant: it has users, **cases**, **archived cases** and **playlists**. Platform administrators curate shared **recommended** question sets keyed by charge. Design: `../specs/001-accounts.md`.

## Commands

```bash
npm run dev                  # nodemon main.js
npm start                    # node main.js
npm run test:unit            # vitest run test/unit (services, policies)
npm run test:http            # vitest run test/http (Supertest against src/app.js)
npx vitest run test/unit/caseService.test.js      # single file
npx vitest run test/unit -t "normalizes"           # single test by name
npm run admin:grant -- someone@example.com [--revoke] | --list   # PLATFORM admin
npm run reset:accounts -- --confirm                # one-off: drops users/cases/playlists (keeps recommended)
npm run job:auto-archive     # scheduled job: archive cases a week after purchase
npm run terms:publish -- terms.txt 11-20-2026   # new Terms of Service version (live at 00:00 UTC that day)
npm run db:sync-indexes [-- --apply]             # dry run (or apply): match DB indexes to the schemas
npm run migrate:question-fields [-- --apply]     # spec 010: strip answers/firstPoll/caseId from questions (not archives)
```

**Indexes:** Mongoose builds missing indexes on startup but never drops one, so after removing an index from a schema run `npm run db:sync-indexes` (dry run), then with `-- --apply`. It drops every index no schema declares, including hand-made ones, so read the dry run first. Don't add a single-field index on a field that already leads a compound index (e.g. `account`): the compound one serves those queries.

**Scheduled jobs** live in `src/jobs/<name>.js` (logic, tested in `test/unit`) with a thin runner in `scripts/<name>.js` (env, DB connect, exit code) and an `npm run job:<name>` script. The scheduler only runs that command: a Render Cron Job now, EventBridge Scheduler → ECS task on AWS later. A runner exits 1 when any item fails so the scheduler flags the run.

`npm test` is a placeholder that exits 1 — use `test:unit` / `test:http`. There is no linter or build step. `migrate:case-category` predates accounts and is obsolete after the reset.

Required `.env`: `PORT`, `NODE_ENV`, `MONGODB_URI`, `JWT_SECRET`, `JWT_EXPIRATION`. Optional: `TRUST_PROXY_HOPS` (default 1). **`MONGODB_URI` must be a replica set** (Atlas is): archiving, registration and the last-admin guard use transactions, which a standalone `mongod` rejects.

## Architecture

- **Entry:** `main.js` (loads env, connects DB via `db.js`, starts `server.js`) → `src/app.js` (cors → helmet → trust proxy → rate limiter → JSON body → routes → error handler). CORS is deliberately first so 429 responses still carry CORS headers. Limiters live in `src/middleware/rateLimiters.js`: the general `apiLimiter` counts signed-in users per user id (verified JWT) and everyone else per IP; `routes/auth.js` adds `credentialLimiter` (login, change-password; failed attempts only) and `registerLimiter`. `trust proxy` defaults to 1 hop (`TRUST_PROXY_HOPS`) so `req.ip` is the client's, not the host's load balancer.
- **Routing:** everything is mounted under `/api` (`src/routes/index.js`); `/auth` is also mounted at the root for backward compatibility.
- **Layering:** routes → controllers → services → models. Services take an `auth` context (not `req`), hold the validation/business logic, and throw `createAppError(message, statusCode, code?)` (`src/utils/error.js`); `errorHandler` turns that into `{ status, message, code? }`. `code` is only ever a string set by the API (e.g. `PASSWORD_CHANGE_REQUIRED`) — numeric driver codes like 11000 are never sent.
- **Size limits:** `src/types.js` bounds case content (`CASE_STUDENTS_MAX` 300, `QUESTIONS_MAX` 100, `QUESTION_OPTIONS_MAX` 20, `QUESTION_TEXT_MAX` 1000, `LABEL_MAX` 200, `ID_MAX` 100) so a case and its permanent archive stay small. Typed fields enforce them in the schemas (`QuestionSchema`, so Playlist and Recommended too, and `caseFields`; `maxItems()` in `Case.js` for array lengths). The Mixed fields (`answers`, `chartData`, `students`) are checked in `src/services/caseContentValidation.js`, used by both `updateCase` and `caseSessionService`: answers are `{ [questionId]: { [studentNumber]: { label, value } } }`; `chartData` may hold only `rects`, whose rects and seats must be flat objects of numbers, short strings, booleans or null. The JSON body limit is 4 MB (a full case at the maxima is about 1.2 MB). `errorHandler` turns Mongoose `ValidationError`/`CastError` into 400 with one message per failing path, so schema limits never surface as 500s.
- **Express 5 async errors:** rejected promises in handlers/middleware are forwarded to the error handler automatically (e.g. `authHandler` just `throw`s).

### Accounts, auth and access

- **`authenticate`** verifies the Bearer JWT, then reloads the user **and their account** on every request: disabled user → 401, suspended account → 403, `mustChangePassword` → 403 `PASSWORD_CHANGE_REQUIRED` (except on `authenticate.allowPendingPasswordChange`, used only by `POST /auth/change-password`). It sets `req.auth = { userId, username, accountId, role, isPlatformAdmin }`, plus `req.user`/`req.userId`. The JWT carries only `{ id, isAdmin }`; account and role are never trusted from it.
- **Terms of Service** (design: `../specs/008-user-agreement.md`): `Agreement` holds one immutable document per version (`termsVersion` is `MM-DD-YYYY`, never compared as a string). The current one is the latest `dateImplemented` ≤ now (`agreementService.getCurrentAgreement`, cached 60 s), and versions are added only by `npm run terms:publish`. Register requires the current `termsVersion` (409 `TERMS_OUTDATED`, 503 `TERMS_UNAVAILABLE` when none is published) and records an insert-only `AgreementRecord` in the registration transaction. `authenticate` blocks every user of an account whose `Account.acceptedTermsVersion` isn't current with 403 `TERMS_ACCEPTANCE_REQUIRED`, except on `POST /auth/change-password` and `POST /agreements/accept` (`authenticate.allowPendingTerms`, account admins only). With no agreement published, nobody is blocked. Sessions carry `mustAcceptTerms`.
- **Two kinds of admin — never conflate them.** `User.role === 'admin'` is the **account admin** (manages the account's users, creates cases, sets owners; gated by `requireAccountAdmin` + `assertAccountAdmin`). `User.isAdmin` is the **platform admin** (writes Recommended sets; gated by `requireAdmin`; granted only by `scripts/grantAdmin.js`). Neither implies the other.
- **`src/policies/accountScope.js` is the only place access filters are built.** Every case/archive/playlist query spreads `caseScopeFilter(auth)` / `archivedCaseScopeFilter(auth)` / `playlistScopeFilter(auth)` / `transactionScopeFilter(auth)` — admins see the whole account, members only cases where they are in `owners`. Out-of-scope records are **404**, never 403, so their existence isn't revealed. Don't hand-write `{ account: … }` filters in services.
- **Users** belong to exactly one account and are disabled, never deleted. Account admins create them with a temporary password (`mustChangePassword: true`). An account must keep one active admin **who has finished password setup** (`mustChangePassword: false`; a pending admin can't act yet): `updateAccountUser` checks this in a transaction that also writes the account document, so two admins demoting each other concurrently conflict instead of both committing (covered by a race test). Refusals are 409 `LAST_ACCOUNT_ADMIN`. An admin can't disable themselves (400 `CANNOT_DISABLE_SELF`, checked before the transaction); another admin can. Handing an account over = promote someone, let them set their password, then demote yourself (spec 020).
- **Cases:** only account admins create them; `account`/`createdBy` are immutable, `owners[]` changes only via `PUT /cases/:id/owners`. `updateCase`'s `allowedFields` whitelist is what keeps those fields out of regular updates.
- **Concurrent edits** (`src/services/caseSessionService.js`): `PUT /cases/:id/questions/:questionId/answers` `$set`s only `answers.<qid>` (the case's only answer store, spec 010), and `PUT /cases/:id/seating` writes `chartData`, `students` and `seated: true`. Admins and owners alike; both return the whole case; a removed question is 409 `CASE_CONFLICT`, a student above `studentNumber` is 400. `Case.revision` (CaseSchema only, never archived) is `$inc`ed by those two and by `updateCase`; `updateCase` checks it when the payload carries `revision` (409 `CASE_CONFLICT` on mismatch, 404 still wins when the caller can't see the case; a missing field matches 0). It is not in `allowedFields`, so clients can't set it.
- **Individual round** (design: `../specs/019-individual-stage.md`): `Case.individualRound` is a Map keyed by `String(student number)` of whole-number point adjustments made outside any question (±`INDIVIDUAL_ROUND_MAX` in `src/types.js`, mirrored as the frontend's `INDIVIDUAL_ROUND_LIMIT`). Written **only** by `PUT /cases/:id/individual-round` (`caseSessionService.saveIndividualRound`; admin or owner): it `$set`s `individualRound.<n>` for each student in the body and `$unset`s those sent as 0 (a missing student is 0), leaves everyone else alone, guards with `studentNumber: { $gte: n }` on the students it sets (clearing is allowed at any number), returns the whole case, and does **not** bump `revision`, because `updateCase` doesn't whitelist the field. Lowering `studentNumber` prunes it along with `studentDetails` (`buildStudentPrune`). Unlike details it is in `caseFields`, so it is archived: the archive's totals and tiers include it.
- **Archiving** (`archiveService`): allowed for an admin or owner once `isCaseComplete` (`src/policies/caseCompletion.js`: every question has ≥1 entry in `case.answers[q.id]`). Inserts an `ArchivedCase` snapshot and deletes the live case in one transaction; `originalCaseId` is unique so a case archives once. `ArchivedCase` reuses `caseFields` from `Case.js` and marks every field immutable on the definitions (Mongoose ignores `immutable()` applied after schema construction). **Automatic archive:** `src/jobs/autoArchiveExpiredCases.js` finds open transactions (`active`/`in_progress`) whose `createdAt` is ≥ 7 days old and calls `autoArchiveCase` for each — no scope, **no completeness check**, `archiveReason: 'purchase'`, `archivedBy: null` (allowed only for `'purchase'`), transaction conclusion `{ manuallyClosed: false, actor: 'auto', actorId: null }`. Cases without a transaction (pre-spec 004) are never swept.
- **Transactions** (`src/models/Transaction.js`, design: `../specs/004-transaction-record.md`) are the purchase record, one per case (`case` is unique), and outlive the case. `src/services/transactionService.js` is the only writer: `createCase` opens one (`active`) in the same MongoDB transaction as the case; `POST /cases/:id/start` moves it to `in_progress` and records `coreFeature` (first call wins); `archiveCase` closes it (`closed`, `termination.*`, `archivedCase`) inside the archive transaction. Every update filters on the current status, so races resolve in the DB and a closed one never changes. Cases created before this have no transaction, and every step treats that as nothing to record. `GET /api/transactions` (account admins, `?status=`, `?limit=` ≤ 200) is read-only. The browser's `timezone` falls back to `'UTC'` (`src/utils/timezone.js`). Stripe fields are placeholders.
- **Student details** (design: `../specs/005-edit-student-data.md`): `Case.studentDetails` is a Map keyed by `String(student number)` of optional, viewer-only `{ age, occupation, gender, race }` (limits in `src/types.js`). Written **only** by `PUT /cases/:id/students/:number/details` (`src/services/studentDetailsService.js`; admin or owner; replaces one entry, all-empty removes it; `studentNumber: { $gte: n }` in the update filter). `updateCase` does not whitelist it, and lowering `studentNumber` prunes entries above it in a transaction. It is defined on `CaseSchema`, **not** `caseFields`, and `archiveService` strips it: details must never reach `ArchivedCase`.
- **Playlists** belong to the account: everyone in it reads them, the creator or an account admin edits/deletes (403 otherwise), titles are unique per account.
- **Recommended sets** are global: any authenticated user reads, only platform admins write. `createdBy` can populate to `null` (author deleted by the reset).
- **Shared question shape:** `QuestionSchema` is defined in `src/models/Case.js` and reused by `Playlist` and `Recommended`: `{ id, text, type, options }` only (spec 010). Answers live only in `Case.answers`; questions have no `answers`, `firstPoll` or `caseId` any more, and strict mode silently drops them from old clients. Documents written earlier keep returning them until `npm run migrate:question-fields -- --apply` runs (`scripts/migrateQuestionFields.js`: cases, playlists and recommended; never archives, which keep them and are read as-is). Question types live in `src/types.js`.

### Case categories and charges

- `src/caseCategories.js` is the catalog. A case stores a single `category` id of the form `<area-slug>.<matter-slug>` (e.g. `criminal.assault`), replacing the old `caseType` + `charge` pair.
- **This file is byte-mirrored with the frontend repo.** Keep it dependency-free, copy changes across, and bump `CATALOG_VERSION`. Ids derive from labels, so renaming a label orphans stored cases and requires a migration — treat the catalog as append-mostly.
- `src/charges.js` derives the distinct "matter" values (charges) from the catalog; it exists separately so the mirrored file stays untouched. `Recommended.charge` is unique and constrained to these, and inputs are resolved case-insensitively onto the canonical spelling (`resolveCharge`). `GET /api/recommended/lookup` accepts either `?charge=` or `?category=` and returns `{ recommended: null }` (200) when nothing is curated.

## Tests

Vitest with `test/setup.js`, which starts a single-node `MongoMemoryReplSet` (transactions need a replica set) and sets `JWT_SECRET`/`JWT_EXPIRATION`. Files run one at a time (`fileParallelism: false`). `test/helpers/fixtures.js` provides `initModels()` (create collections + indexes up front — call it in `beforeAll`, transactions can't create collections implicitly), `resetDb()`, `makeAccount({ admins, members, disabled })` with `authFor(user)`, `makeCase()`, `makeTransaction()` (`makeCase` creates no transaction, like a pre-transactions case), `answerAll()` and `seedAgreement()` (registration needs a published agreement and `termsVersion: TERMS_VERSION`; `resetDb()` also clears the agreement cache). A model a transaction writes to must be in the fixtures' `MODELS` list, because a MongoDB transaction can't create a collection. Unit tests call services with an `auth` context; `test/http/` drives the real app with Supertest.
